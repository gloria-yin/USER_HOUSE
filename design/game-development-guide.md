# 玩伴小屋游戏开发规范

本文档是新增、拆分或重构小游戏时的必检清单。游戏不只要“能开局和结算”，还必须把返回、关闭、暂停、页面隐藏和恢复当成完整生命周期设计。

## 必须遵守的存档契约

1. 可继续的状态必须是可 JSON 序列化的纯数据，不得保存 DOM、Canvas context、定时器、Worker、函数或循环引用。
2. 每次有效操作后要调用 `saveProgress(gameId, state)`。动画、物理或定时驱动游戏还应周期保存，但要节流。
3. 返回、关闭、暂停、`visibilitychange` 和 `pagehide` 前必须强制保存最新状态，不能只等延迟写入定时器。
4. 模块化游戏必须返回 `{ save, destroy, getState }`。`save()` 要立即持久化；`destroy()` 要先保存，再清理 animation frame、定时器、Worker、Observer 和事件监听。
5. 暂停期间不得推进物理、AI 回合、倒计时或游戏时长。恢复前统一经过 3 秒倒计时。
6. 只有正常结束、主动结算或用户确认重开才能调用 `clearProgress(gameId)`。返回和关闭绝对不得清档。
7. 退出时要保存或更新同一条“进行中”游戏记录；恢复后最终结算应更新该记录，不得重复新建多条。进行中记录不发放宠物奖励，也不当作胜负结果。

## 状态设计

存档至少要包含：

- 足以精确重建当前局面的核心数据；
- 分数、关卡、回合、道具、随机种子或已生成题面；
- 用于语录、小剧场和日志的 `details`；
- 恢复后必须继承的角色快照、已触发语录和有效游戏时长。

对正在执行的临时动画要明确规则：要么在强制保存时原子提交，要么回退到动画前的稳定状态。不允许保存一半动画、却丢掉对应逻辑修改。

## 退出与恢复验收

每个新游戏发布前都必须手动验证：

- 开局后立即返回，再进入可看到继续提示；
- 操作后在 700ms 内关闭小屋，最后一步仍然存在；
- 暂停、切换后台、恢复，局面不变且离线时间不计入；
- 刷新 SillyTavern 后可恢复，角色、头像、分数、道具和详细数据属于同一局；
- 多次退出同一局只更新一条进行中记录；
- 继续后正常结束，进行中记录被替换为最终结果；
- 确认重开后不会被旧控制器再次写回旧存档；
- 游戏结束后不再出现“继续上次进度”。

## 数据兼容与体积

- 状态结构改动时增加 `version`，读取旧存档时做有界默认和字段迁移。
- 存档数组要限制长度；历史、撤回栈和日志不得无限增长。
- 写入本地存储必须捕获容量不足等异常，并读回校验本次内容；未通过校验不得向用户显示“已保存”。
- 通用样式放在 `style.css`，避免在运行时重复注入大段 CSS。游戏模块只保留真正独立且只注入一次的样式。
- 关闭游戏时必须清理所有资源，否则反复进入会叠加计时器、事件和 Worker。
