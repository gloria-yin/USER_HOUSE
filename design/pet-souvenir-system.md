# 灵息信箱与纪念品收藏系统设计

> 文档状态：功能规划稿  
> 适用范围：宠物屋、遛弯/RP 陪伴、日常互动、同一 `char` 名下的往期宠物  
> 核心目标：不新增宠物立绘或动作素材，用文字、现有宠物形象和纸张式 UI，把一次次互动沉淀成可回看、可回复的关系记忆。

## 1. 系统定位

这不是以稀有度和刷取为核心的掉落系统，而是一只宠物与 `user`、`char` 共同生活留下的收藏匣。

系统应做到：

- 当前宠物在遛弯、玩耍、完成剧情等有明确“结束点”的互动后，有概率带回纪念品、明信片或短笺。
- 同一 `char` 以前养过、已经完成结局的宠物，每天有一次独立概率从灵息世界寄来物品、明信片或信件。
- 收藏内容能引用真实发生过的遛弯 RP、剧情记录和照料日志，但不能把模型臆造的事件写成既定回忆。
- 明信片和信件允许 `user` 回复。回复会永久保存在对应物件上，并能在下一次来信里得到自然回应。
- 只有玩家点击“接收”才调用模型。概率命中只创建一个本地待接收事件，避免无意义的 API 消耗。
- 所有收藏归属于同一位照料者/`char` 的收藏匣，而不是归属于当前宠物。更换宠物后仍可查看旧收藏和旧宠来信。
- 不依赖新增动画。现有宠物立绘、CSS 纸张、邮戳、封蜡、标签和简单图标即可完成表现。

## 2. 世界观解释

宠物不必真的会握笔。宠物屋右下角新增一个“灵息信箱”：

- 当前宠物带回的东西会被信箱登记，并把叫声、爪印、气味或灵息翻译成一段给 `user` 的话。
- 往期宠物可以从灵息世界的驿站投递。信箱会保留它原本的口吻，不把所有宠物都写成同一种成年人书信腔。
- 普通路线宠物的去向必须服从它实际完成的结局。若结局没有明确说明它生活在灵息世界，不应强行改写；可以写成“灵息驿站代转”“边界来信”或沿用结局里已经建立的所在地。
- 信箱只是翻译和转交媒介，不应成为替宠物发言、解释剧情的旁白角色。

## 3. 内容类型

### 3.1 纪念品 `souvenir`

适合当前宠物从日常互动里捡回，也适合往期宠物随信寄来。

必须展示：

- 名字：4～12 个汉字，具体、有辨识度，避免“神秘的礼物”一类空泛名称。
- 外观描述：材质、颜色、触感、气味、磨损或细节，80～160 字。
- 来历：它在什么互动或地点被发现；只引用真实上下文。
- 给 `user` 的话：40～100 字，符合宠物性格、成长阶段与双方关系。
- 赠送者、获得日期、来源事件。
- 关联回忆：若使用了真实日志或剧情，显示一个可跳转的“回忆标签”；没有可靠回忆时不显示。

不设置战力、售价和强制稀有度。可用“路边小物、手作物、灵息物、旧日物件”等分类帮助筛选，但不能把收藏匣做成抽卡背包。

### 3.2 明信片 `postcard`

明信片强调“它现在看见了什么”以及一问一答的互动感。

必须展示：

- 正面题名或地点名。
- 正面景象文字：用 50～110 字写出一幅可想象的画面，不要求生成新图片。
- 邮戳、投递日期、寄件宠物、收件人。
- 背面正文：180～360 字。
- 一个真正容易回答的问题，不能用“你想我吗”反复制造负担。
- 2～3 条可选短回复，以及“自己写”入口。
- `user` 实际发送的回复原文。
- 若后续来信回应过这张卡，展示“它后来回了什么”并链接到后续收藏。

建议采用延迟回信：玩家回复后不立即再调用一次模型，而是把回复放入该宠物的待回应队列；下一次它寄来东西时，提示词要求自然回应。这比即时生成一段万能回答更像持续通信，也节省调用次数。可在后续版本增加“现在等一封短回信”作为可选功能。

### 3.3 信件 `letter`

信件适合往期宠物、剧情里程碑或较长时间未见后的联系，不应在每次摸宠后频繁出现。

必须展示：

- 主题、称呼、日期、正文、落款；正文建议 450～750 字。
- 可以有一段不超过 100 字的附言。
- 可附带一个纪念品，但附件仍作为独立收藏项保存，并互相链接。
- 可以提出一个问题，允许 `user` 回信。
- 回信保留原文、发送时间和被哪一封后续来信回应。

### 3.4 投递包 `delivery`

“投递”是触发层，不是第四种收藏类型。一次投递包含：

- 一件纪念品；或
- 一张明信片；或
- 一封信；或
- 一封信/明信片加一件附件纪念品。

MVP 阶段一次投递最多生成两个收藏项，避免弹窗过长和模型输出不稳定。

## 4. 完整运作流程

```text
互动结束 / 每日旧宠检查
        ↓
本地检查：接收开关、冷却、每日上限、事件是否重复
        ↓
本地概率命中，只建立 pendingDelivery，不调用模型
        ↓
出现“有一份投递”弹窗，同时右下角信箱增加未读角标
        ↓
玩家选择：接收 / 稍后 / 本次不收
        ↓
点击接收才整理上下文并调用模型
        ↓
JSON 校验 → 保存收藏 → 展示拆封结果
        ↓
玩家可收藏、回复、从关联标签回看当时的日志或故事
```

三个按钮的行为：

- **接收**：立即调用模型。生成期间锁定该投递，避免重复点击。
- **稍后**：保留在信箱队列，不调用模型；之后可从信箱面板重新打开。
- **本次不收**：删除这一次待投递，不调用模型，不关闭总接收开关。

若关闭接收功能：

- 不进行概率抽取，也不制造后台积压。
- 不累计“错过了几百封信”的补偿队列。
- 重新开启后，从当天之后正常计算；关闭期间不会影响往期宠物关系。

待接收队列最多保存 3 个事件。队列满时暂停新抽取，避免用户久未打开后被连续弹窗打扰。

## 5. 触发规则与概率

### 5.1 当前宠物

每个合格事件结束时独立判断，但必须通过冷却和每日上限。

| 合格事件 | 建议基础概率 | 限制 |
| --- | ---: | --- |
| 遛弯/RP 返回宠物屋 | 28% | 本次至少产生 1 条有效 RP 回复或持续 2 分钟；每次遛弯只结算一次 |
| 支线故事完成 | 18% | 同一个故事 ID 只结算一次 |
| 主线故事完成 | 15% | 同一个故事 ID 只结算一次；结局流程不触发当前宠物远方来信 |
| 有效照料小段结束 | 8% | 饱食或快乐实际增加；6 小时内最多结算一次，不按每次点击结算 |
| 顶球/小游戏完成 | 10% | 达到有效完成条件；每天最多结算一次 |

推荐限制：

- 当前宠物常规投递每天最多 1 次。
- 重要主线里程碑可额外允许 1 次，但当天所有来源合计不超过 2 次。
- 连续 4 个合格事件未命中时，第 5 个合格事件必定创建投递；命中、拒收或关闭功能都会重置相应计数。
- 蛋阶段默认不触发，避免提前泄露物种、名字、性别和灵息特征。孵化后再开启当前宠物投递。
- 同一个 `eventKey` 永远只能命中一次，刷新页面或重复进入结算页不能重复刷取。

当前宠物内容权重建议：纪念品 60%、明信片 40%。若当天事件是长时间遛弯，可把明信片提高到 55%。当前宠物默认不寄正式长信；若以后希望让剧情里程碑产生短笺，可作为第二阶段的特殊规则加入。

### 5.2 同一 `char` 的往期宠物

每天第一次打开宠物页面时，对当前照料者名下所有已完成结局的往期宠物进行一次总判断，而不是让每只宠物各抽一次。否则养过的宠物越多，弹窗会指数式变吵。

- 有至少一只往期宠物时，每日基础投递概率 22%。
- 连续 4 个检查日未命中，第 5 个检查日必定命中。
- 每位 `char` 每天最多 1 份往期宠物投递。
- 先判断“今天有没有投递”，再选择寄件宠物。
- 寄件人优先选择很久没有寄信的宠物，并降低连续两次选择同一只的权重。
- 已有未拆往期投递时，不再产生新的一封。
- “一天”使用玩家本地时区的日期键，避免 UTC 跨日造成重复触发。

寄件宠物选择权重可按以下方式计算：

```text
weight = 1
       + min(30, 距离上次寄件天数) × 0.08
       + 尚未寄过信 ? 1.5 : 0
       - 与上次寄件人相同 ? 1.2 : 0
```

往期宠物内容权重建议：纪念品 30%、明信片 35%、信件 35%。若存在一封未被回应的玩家回信，则优先生成能自然回应它的明信片或信件。

### 5.3 防刷与防重复

- 摸宠、喂食等连续点击合并成一次“照料小段”，不按按钮点击次数抽取。
- 遛弯必须有有效 RP 内容或达到最低持续时间，打开后立刻退出不结算。
- 保存最近 12 件收藏的标题、核心物件、地点和主题标签，生成时要求避开近似内容。
- 同一段剧情回忆默认只作为核心素材使用一次；以后可以轻轻提到，但不能反复改写成不同“新礼物”。
- 不使用“普通、稀有、史诗”刺激重复刷取。收藏价值来自具体经历和宠物关系。
- 每个收藏匣建议软上限 300 件。达到上限时提示导出或整理，不可静默删除旧收藏。

## 6. 右下角灵息信箱

宠物页面右下角放置一个常驻“灵息信箱”按钮，使用现有 UI 风格和 CSS 图标即可，无需新宠物动画。

按钮状态：

| 状态 | 表现 |
| --- | --- |
| 接收开启、无待收 | 信封/小包裹图标，低调常驻 |
| 有待收投递 | 角标显示数量，轻微一次性晃动；不要循环闪烁 |
| 有未读收藏 | 小圆点角标，与“待接收数量”区分 |
| 接收关闭 | 图标变灰并带斜线，仍可点击查看旧收藏 |
| 正在生成 | 显示拆封中的纸条进度，禁用重复接收 |

点击按钮打开底部抽屉：

```text
┌────────────────────────────┐
│ 灵息信箱              ● 2  │
│ 接收宠物带回的东西      [开] │
│ 接收往期宠物来信        [开] │
│                            │
│ 待接收                     │
│ · 它从今天的遛弯里带回了什么 │
│ · 一份从远处寄来的投递       │
│                            │
│ [查看收藏匣]   [投递说明]    │
└────────────────────────────┘
```

推荐保留两个开关：

- “接收宠物带回的东西”：总开关。
- “接收往期宠物来信”：只有总开关开启时有效，允许不想被旧宠打扰的玩家单独关闭。

开关状态按 `char/caretaker` 保存。切换到另一位角色时，可以拥有不同的收藏匣和接收偏好。

## 7. 触发弹窗与拆封体验

### 7.1 当前宠物弹窗

```text
┌────────────────────────────┐
│            有东西被带回来了  │
│                            │
│  [使用当前宠物已有立绘]       │
│  它回屋后一直护着爪边的小包裹，│
│  看样子很想让你亲手打开。      │
│                            │
│ [本次不收] [稍后] [接收]       │
└────────────────────────────┘
```

弹窗文案只描述可见动作，不提前说出具体物件，也不擅自规定蛋色、宠物能力或玩家反应。

### 7.2 往期宠物弹窗

```text
┌────────────────────────────┐
│          灵息驿站送来一封投递 │
│  寄件人：往期宠物名 · 物种     │
│  邮戳边缘留着熟悉的小爪印。     │
│                            │
│ [本次不收] [稍后] [接收]       │
└────────────────────────────┘
```

这里可以显示往期宠物保存下来的现有形象缩略图。若旧存档缺少可靠外貌资料，只显示名字与物种，不用当前宠物的形象代替。

### 7.3 接收与失败

- 点击接收后显示“正在拆封”，而不是空白 loading。
- 生成成功后先保存，再打开详情，防止关闭弹窗导致内容丢失。
- 模型输出无法解析时自动用同一上下文修复一次。
- 第二次仍失败、API 未配置或断网时，保留原待接收事件并显示“投递还在路上，可以稍后重试”。不要保存一件内容残缺的占位收藏。
- 生成请求超过设定超时时间后，将状态从 `generating` 恢复为 `pending`，允许再次接收。

## 8. 收藏匣页面

收藏匣建议作为现有宠物记录/图鉴弹窗中的一个新入口，也可以从灵息信箱直接打开。两处进入同一页面，不建立两套数据。

### 8.1 总览

```text
┌──────────────────────────────────────┐
│ 灵息收藏匣              搜索  筛选    │
│ 全部  纪念品  明信片  信件  往期宠物  │
│                                      │
│ ┌──────────┐ ┌──────────┐            │
│ │ 三折风票  │ │ 苔光水道  │            │
│ │ 小鹿 · 今天│ │ 溪团 · 8/28│            │
│ │ 一片被…   │ │ “这里的水…”│            │
│ └──────────┘ └──────────┘            │
│                                      │
│ ┌──────────┐ ┌──────────┐            │
│ │ 树洞来信  │ │ 河湾圆石  │            │
│ │ 往期宠物  │ │ 水獭 · 收藏│            │
│ └──────────┘ └──────────┘            │
└──────────────────────────────────────┘
```

筛选项：

- 类型：全部、纪念品、明信片、信件。
- 寄件宠物：当前宠物、某只往期宠物。
- 来源：遛弯、照料、小游戏、剧情、灵息来信。
- 状态：未读、已回复、等待回应、已收藏。
- 日期：按月或成长周期。

桌面端使用 2～3 列卡片，窄屏单列。卡片只显示标题、寄件宠物、日期、一行摘要和状态角标，完整正文进入详情页阅读。

### 8.2 纪念品详情

采用“小型博物签”式布局：

- 上部是名称和简洁的类别印章。
- 中部用现有宠物形象的小头像配合文字描述，不需要为物件生图。
- 下部是“它为什么带回来”“它想对你说”和关联回忆。
- 底栏显示收到日期、赠送者、收藏星标。

### 8.3 明信片详情

不必制作真的 3D 翻转动画，使用“正面 / 背面”两个标签页更稳定、也更适合移动端：

- 正面：CSS 渐变纸面、地点题名、景象文字、邮戳。用排版让文字本身形成画面。
- 背面左栏：寄来的正文和落款。
- 背面右栏：`user` 名称、邮票/爪印式装饰和日期。
- 下方：独立的通信串，依次显示宠物来信、`user` 回答、宠物后来的回应。

### 8.4 信件详情

- 米白纸张、略深正文、清晰行距，不用大面积花纹影响阅读。
- 抬头与日期靠右，落款保留宠物特有的爪印、毛团或灵息印记描述。
- 附件纪念品用纸夹样式放在正文之后，点击进入它的独立详情。
- 回复区采用普通文本框，提供 2～3 个可编辑的建议回复。任何建议被选择后也应允许继续修改。

### 8.5 视觉规范

- 纪念品：暖米色、木棕、低饱和绿。
- 明信片：雾蓝、浅杏、灰粉，根据地点标签小幅变化。
- 信件：纸白、墨褐、暗金封蜡。
- 往期宠物投递：增加一枚小型星点/灵息邮戳，不把整个页面染成幽灵色。
- 动效只用于第一次收到时的短暂拆封、纸张展开和未读角标；尊重“减少动态效果”设置。
- 所有状态不能只靠颜色表达；图标旁保留“未读、待回复、来自往期宠物”等文字。
- 正文支持字号调整，并保证移动端按钮至少 44px 的可点击高度。

## 9. 回复机制

### 9.1 推荐流程：延迟回应

1. 玩家在明信片或信件详情输入回复。
2. 原文立即本地保存，状态变为“等待它的回应”。此时不调用模型。
3. 下一次该宠物被选为寄件人时，将最早一条未回应回复和最多一条较新的回复加入上下文。
4. 新投递需要自然回应，但不能整封信只围绕回复打转。
5. 新投递保存后，在旧卡片上标记“已在《新收藏标题》中回应”，并建立双向链接。

这样既能形成连续通信，又不会让每次打字都产生额外调用。

### 9.2 可选流程：立即短回音

后续若增加“等它回一句”按钮，可以单独调用模型生成 80～180 字的短回应。它只作为通信串内容，不计为新的收藏，也不参与每日投递上限。

### 9.3 回复边界

- `user` 的原文不得被模型改写。
- 建议回复不能替 `user` 宣布强烈情绪、承诺或关系变化。
- 玩家删除自己的回复时，只删除本地回复；已经生成的后续信件不回滚。
- 每件来信最多挂一条正式回复，可在发送前反复编辑，避免线程无限分叉。

## 10. 数据模型

### 10.4 往期宠物资料兼容

正式养成模式中，已完成宠物仍位于同一 `caretaker.pets`，可以读取它自己的 `infoText`、故事、日志和结局。固定/试玩模式现有 `archives` 若只保留结局摘要，无法可靠还原旧宠外貌和口吻。

实现本系统前应在宠物完成结局时额外保存紧凑快照：

- 名字、物种、性别、路线、性格、灵息能力、成年外貌。
- 结局发生时间和明确去向。
- 3～8 条最重要的真实回忆 ID/摘要。
- 它最后一次寄件日期。

旧版本存档迁移时，能从该宠物自己的 `infoText` 解析多少就保存多少；缺少的字段显示“未记录”，不能借用当前宠物资料，也不能让模型补写成事实。

## 11. 提供给模型的上下文

每次点击接收时才整理上下文，并只提供生成当前收藏所需的部分：

- `user`、`char` 的称呼与当前关系摘要。
- 寄件宠物自己的资料卡、路线、阶段、性格、外貌和灵息能力。
- 当前宠物：刚结束的事件摘要，以及最多 6～8 条相关 RP 消息的压缩摘要。
- 往期宠物：真实结局与去向、1～3 条相关历史回忆、距离上次来信的时间。
- 当前宠物与往期宠物最近 12 件收藏的标题/标签，用于去重。
- 最多 2 条等待这只宠物回应的 `user` 回复。
- 明确列出“不确定或未设定的字段”，要求模型不得自行补全。

不要把完整聊天、全部日志和所有故事每次都塞进提示词。先在本地选取相关记忆，既减少 token，也降低模型把不同周目混在一起的风险。

## 12. 写作规范

### 12.1 总体文风

- 像故事中的真实物件和通信，自然进入画面，不以“总分、任务完成、事件说明、根据数据”等解释性内容开头。
- 可爱、治愈、活泼，但不幼稚到每句话都叠语气词。
- 使用具体动作和感官细节：爪印怎样歪、纸角沾了什么、宠物怎样把东西推向 `user`。
- `user` 与 `char` 都是关系中的活人，可以互相打趣、抢着拆信、被宠物调动；不能只把 `char` 写成旁观说明员。
- 保留适度的小意外、小得意和轻微拉扯，让互动有张力，但不靠生离死别强行煽情。
- 宠物口吻由性格决定。胆小、骄傲、黏人、爱闯祸的宠物写法应明显不同。
- 往期宠物有自己的新生活，不应永远停在悲伤地想念玩家；它可以分享邻居、工作、天气、探索和小麻烦。

### 12.2 连续性规则

- 只能把输入中明确出现的事件写成共同回忆。
- 缺少可靠回忆时，写当下观察、灵息世界生活或温柔的泛化牵挂，不虚构一次具体旅行、礼物或承诺。
- 不提前透露未孵化宠物的物种、性别、名字、蛋色、灵息能力和成年形态。
- 不改变已经确定的动物外貌、颜色和形态。
- 不把普通路线宠物突然写成拥有未设定的法术。
- 不替 `user` 决定感受、动作、台词或回信内容。
- 若回应玩家旧信，先回应其中一个具体细节，再自然写自己的近况，避免复述整封信。
- 相同意象、礼物、地点和句式不能连续出现。

### 12.3 不应出现的写法

- “本次互动共获得 8 点成长值，因此……”
- “这是一件稀有纪念品，证明你完成了任务。”
- “粉色的蛋对此表示反对……”（蛋色并未由上下文确定。）
- “你感动得流下眼泪并答应永远等我。”（替玩家决定反应。）
- 每封信都写“我在这里很好，我很想你”，却没有新的生活细节。

**三折风票**

**来历**：它在遛弯回程时从长椅底下扒出来，先自己踩住，等 `char` 假装没看见，才很郑重地推到 `user` 鞋边。

- “有，而且我们还没找到。”

## 15. 与现有宠物系统的接入建议

### 15.1 现有结构对应关系

后续实现时可沿用目前运行层的这些入口：

- `petFullData()` / `caretaker.pets`：取得同一 `char` 名下的当前与往期宠物。
- `petFullPetCompleted(pet)`：筛选已经完成结局、可参与每日寄件的宠物。
- `petFullAllLogsText(caretaker)`：可作为记忆检索来源，但不能把返回的全部文字直接塞给模型；应先按寄件宠物和事件选取 1～3 条。
- `petCaretakerPromptConfig(caretaker)` 与 `callApiText(...)`：复用该照料者已经选择的模型设置，在点击接收后发起生成。
- `openPetRecords(info)`：收藏匣可以作为现有记录弹窗的新页签，信箱按钮则直接定位到该页签。
- `STORAGE_PET_FULL`、`STORAGE_PET_TEST`：继续保存宠物本体；收藏建议使用新的 `STORAGE_PET_COLLECTIONS = SCRIPT_ID + '_petCollections_v1'`，避免被单周目状态重置。

### 15.2 事件接入

各功能只负责发出统一的“合格事件结束”信号，不直接生成收藏：

```js
maybeQueuePetDelivery({
  caretakerId,
  petId,
  eventKey,
  kind,
  happenedAt,
  location,
  interactionSummary,
  relatedStoryIds
});
```

这样遛弯、小游戏、剧情和日常照料共用概率、每日上限、防刷和待接收逻辑。

### 15.3 往期宠物检查

```js
checkFormerPetDailyDelivery(caretakerId, localDateKey);
```

调用时机为进入宠物主页或切换照料者后。它只能每天执行一次概率判断，不能在每次页面重绘时重复抽取。

### 15.4 RP 联动

遛弯结束时保存一份专用于收藏生成的短摘要：

- 本次去了哪里。
- 宠物做了哪两个最有辨识度的动作。
- `user`、`char` 各自参与了什么。
- 是否出现可以成为物件来源的具体环境细节。
- 对应消息范围或消息键，供“关联回忆”跳转。

摘要只记录事实，不预先替模型写成礼物。若聊天内容与宠物无关或没有足够事实，模型可以生成普通的小物，但不得声称它来自不存在的场景。

### 15.5 导入、导出与删除

- 现有宠物存档导出应同时包含收藏匣、待投递和回复线程。
- 删除某只当前宠物时，已有收藏不跟随删除；详情标记为“往期记录”。
- 删除整个照料者/`char` 的宠物数据时，需要单独确认是否连收藏匣一并删除。
- 清空待投递与清空收藏必须是两个操作，且都需要确认。

## 16. 伪代码

```js
function onEligiblePetEvent(event) {
  const box = getCollectionBox(event.caretakerId);
  if (!box.receiveEnabled) return;
  if (!isHatched(event.petId)) return;
  if (box.pendingDeliveries.length >= 3) return;
  if (hasHandledEventKey(box, event.eventKey)) return;
  if (!passesEventCooldown(box, event)) return;
  if (reachedDailyCurrentLimit(box, event)) return;

  const forced = box.counters.currentMissStreak >= 4;
  if (!forced && Math.random() >= chanceFor(event.kind)) {
    box.counters.currentMissStreak += 1;
    rememberHandledEventKey(box, event.eventKey);
    saveBox(box);
    return;
  }

  box.pendingDeliveries.push(buildPendingDelivery(event));
  box.counters.currentMissStreak = 0;
  rememberHandledEventKey(box, event.eventKey);
  saveBox(box);
  showDeliveryPopup();
}

function checkFormerPetDailyDelivery(caretakerId, todayKey) {
  const box = getCollectionBox(caretakerId);
  if (!box.receiveEnabled || !box.formerPetMailEnabled) return;
  if (box.counters.lastFormerPetRollDate === todayKey) return;

  box.counters.lastFormerPetRollDate = todayKey;
  const formerPets = getCompletedPetsWithOwnSnapshot(caretakerId);
  if (!formerPets.length || hasPendingFormerDelivery(box)) {
    saveBox(box);
    return;
  }

  const forced = box.counters.formerMissStreak >= 4;
  if (!forced && Math.random() >= 0.22) {
    box.counters.formerMissStreak += 1;
    saveBox(box);
    return;
  }

  const sender = weightedFormerPetChoice(formerPets, box);
  box.pendingDeliveries.push(buildFormerPendingDelivery(sender, todayKey));
  box.counters.formerMissStreak = 0;
  saveBox(box);
  showDeliveryPopup();
}
```

创建 pending 后即记录 `eventKey` 已处理。即使玩家选择“本次不收”，也不能靠重复进入同一结算重新抽取。

## 17. 开发阶段

### 第一阶段：最小可用闭环

- 照料者级收藏存储和旧存档快照迁移。
- 右下角灵息信箱、两个接收开关、待接收角标。
- 遛弯结束和往期宠物每日检查两种触发。
- 接收/稍后/本次不收弹窗。
- 三种收藏类型、严格 JSON 协议、校验与一次修复。
- 收藏匣总览、详情、未读、星标。
- 明信片/信件回复保存，以及“等待回应”状态。

### 第二阶段：丰富日常

- 接入照料、顶球、主线和支线结束事件。
- 延迟回信：下一封投递回应 `user` 旧回复并自动建立双向链接。
- 信件附带纪念品。
- 搜索、筛选、关联回忆跳转和收藏导出。

### 第三阶段：关系延续

- 当前宠物偶尔发现往期宠物留下的旧物，但只能引用真实收藏，不能虚构两只宠物见过面。
- `char` 在 RP 中可通过简短、可选的上下文注入提到最近收到的信，例如桌上摆着哪张明信片。
- 玩家可勾选 1～3 件收藏作为下一次遛弯的“随身物”，只影响文字上下文，不增加新立绘或数值。

## 18. 验收清单

- [ ] 关闭接收后不抽取、不弹窗、不调用模型，旧收藏仍能查看。
- [ ] 概率命中时不调用模型；只有点击“接收”才调用。
- [ ] 刷新页面、重复打开结算、连续点击接收都不会生成重复收藏。
- [ ] 同一 `char` 的往期宠物每天最多产生一次总投递判断。
- [ ] 更换当前宠物后，原收藏、玩家回信和往期宠物寄件记录仍存在。
- [ ] 当前宠物和往期宠物使用自己的资料，绝不串用另一只宠物的外貌或能力。
- [ ] 模型不知道蛋色时不会自行指定颜色；孵化前不会泄露物种。
- [ ] 明信片清楚显示写了什么、`user` 回复了什么、后续在哪一封信回应。
- [ ] API 失败时待投递仍在，可以重试，不产生半成品收藏。
- [ ] 近似标题、同一回忆和同一寄件宠物不会短期连续重复。
- [ ] 收藏页在桌面和移动端均能完整阅读，不依赖新增宠物动画或图片。
- [ ] 文案自然开场，不出现总分、成长值、任务说明或模型术语。
