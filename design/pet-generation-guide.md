# 新宠物完整生成引导

本文件仅用于设计、生成和接入新宠物，不参与游戏运行。文中资源路径均以项目根目录为基准。

你需要为“玩伴小屋”从零设计、生成、后处理并整理一只完整可用的新宠物。

目标：制作可爱、治愈、适合长期陪伴的像素宠物，并将最终运行时图片放入 assets/pets/<species>/。中间生图、测试图和失败版本只能放在临时设计目录，不得当成正式资源。

请严格按下面顺序完成。先检查现有资源和环境，再确定角色设计，之后生成母版、动作表、透明图和运行时精灵图。不得跳过透明度检查、人工预览或最终验证。

---

# 一、先理解现有宠物系统

开始前必须检查：

- assets/pets 中至少两只现有宠物的 preview.png、三形态动作图、manifest.json、CSS 和 README。
- 当前宠物资源加载代码对 species key、形态和状态的要求。
- 是否已有同名宠物目录，禁止未经用户允许覆盖现有宠物。
- 当前工作区是否存在用户未提交的修改，禁止覆盖无关改动。
- 可用生图工具、后处理脚本和 Python 环境。

先用一句话明确：

“这只宠物本质上是：具有哪些固定物种特征、成长差异和灵息变异特征的可爱陪伴动物。”

不要把现有宠物的耳朵、尾巴、脸纹或身体结构混入新动物。

---

# 二、正式资源规格

每只宠物必须完整覆盖：

- 形态：baby、adult、magic。
- 状态：normal、happy、eat、sleep、sad。
- 每个状态 4 帧。
- 每帧 128 × 128 像素。
- 每个状态输出一张 512 × 128 RGBA PNG 横向精灵图。
- 每只宠物合计 3 × 5 × 4 = 60 帧。
- 默认播放速度每帧 500ms。
- 最终背景必须透明。
- 缩放显示时保持像素风，不得出现背景色块。

正式目录必须为：

assets/pets/<species>/
  baby/
    normal.png
    happy.png
    eat.png
    sleep.png
    sad.png
    full.png
  adult/
    normal.png
    happy.png
    eat.png
    sleep.png
    sad.png
    full.png
  magic/
    normal.png
    happy.png
    eat.png
    sleep.png
    sad.png
    full.png
  preview.png
  manifest.json
  <species>.css
  README.md

species key 只使用小写英文字母，避免连字符被当前运行时代码过滤。例如：

- redpanda，不使用 red-panda。
- sikadeer，不使用 sika-deer。

# 三、总体美术要求

统一风格：

- 可爱治愈系手工像素插画。
- 圆润、友好、柔软，不恐怖、不凶恶、不写实。
- 有明确的深色像素轮廓，但不要用纯黑粗线包住整个身体。
- 使用簇状明暗、有限色板和统一像素颗粒。
- 不生成衣服、文字、编号、水印、UI、场景或其他动物。
- 不生成地面、投影、接触阴影、反射或背景装饰。
- 主体和耳、尾、角、刺、灵息特效四周保留足够裁切空间。
- 在 128 × 128 下仍能一眼识别物种和形态。
- 表情温柔可亲，低落动作也不能阴森或夸张痛哭。

幼年和成年要求：

- 普通形态的设计一旦通过，后续不得擅自改色或重画身份。
- baby 头更大、身体更短圆、动作稍显笨拙。
- adult 身体略成熟、四肢或尾巴更有力量，但仍保持可爱比例。
- 幼年与成年不是简单等比缩放，必须有可读的成长差异。
- 脸纹、眼睛、耳尾特征和主色必须保持同一身份。

灵息形态要求：

- magic 必须比成年形态更不一样，允许整体换色、明显变异和轮廓变化。
- 仍必须保留足够的物种识别点和同一角色的脸部身份。
- 变异应表现为可爱、柔软、治愈的灵息动物，禁止恐怖、腐化、骷髅、尖牙、血污、邪恶红光或压迫感。
- 不得只给成年形态加一圈光；至少增加一项轮廓变化、一项固定灵息器官或纹样、一项轻量动态特效。
- magic 的标准姿势和动作节奏可以、也应当与 adult 不同，体现新身体结构。
- 灵息特效不得遮挡脸、眼睛、主要四肢或动作。
- 即使整体换色，脸型、物种器官和关键花纹仍需连续可认。

# 四、当前五只已确认宠物的身份规则

如果任务是继续当前方案，必须严格继承下面的最终设计。普通形态已经通过，不得重新设计。

## 1. 水獭 otter

普通形态：

- 亚洲小爪水獭方向。
- 可可棕短毛、奶油色口鼻与喉胸斑。
- 圆耳、黑亮眼睛、粗长渐尖尾。
- 幼年圆短，成年稍修长。

灵息形态：

- 整体以白色为主，不沿用普通形态的可可棕主色。
- 保留水獭短圆耳、口鼻结构和有力尾巴。
- 可加入柔和水纹、水带、青蓝微光或漂浮水滴。
- 不得变成幽灵、苍白尸体或阴森海兽。
- 动作可更多使用漂浮、拨水、尾巴带动水流，与成年陆地动作区分。

## 2. 刺猬 hedgehog

普通形态：

- 杏色脸和肚皮、椒盐色短刺。
- 圆耳、黑色纽扣眼、小尖鼻。
- 幼年像短刺圆球，成年刺层更饱满。

灵息形态：

- 保留当前通过的晶刺方案。
- 身体可使用深紫或蓝紫，晶刺使用明亮天蓝、紫色和少量橙金色。
- 晶刺必须鲜亮可爱，不能做成血色、毒刺或恐怖尖刺。
- 可有短促电弧或闪光，但不能遮挡脸。
- 动作突出晶刺闪动、轻弹、卷球后探脸，与成年普通刺猬动作不同。

## 3. 小熊猫 redpanda

普通形态：

- 红棕身体、奶白脸纹、深棕四肢。
- 圆耳、粗大环纹尾。
- 幼年头大身短，成年更轻快。

灵息形态：

- 整体以暗红色和黑色为主，可以明显不同于普通红棕配色。
- 必须保持可爱、温暖、治愈，避免邪恶、血腥或恐怖感。
- 可以使用暖金色眼睛、环纹灯带、叶片状耳饰或少量暖色光尘。
- 只能有一条尾巴。
- 尾根必须从身体右后方臀部连续长出。
- 第一段环纹必须紧接臀部，不能出现断尾、漂浮尾巴或独立尾圈。
- 灵息小熊猫不得把尾巴抱在怀里；尾巴保持在身体后方或右后侧。
- 每一帧都必须检查尾根连接，不能只检查第一帧。
- 动作应使用后摆环尾、侧身转尾、耳部光翼和轻跳，避免沿用成年抱尾动作。

## 4. 羊驼 alpaca

普通形态：

- 华卡约羊驼方向。
- 奶白或浅焦糖卷毛、短圆脸、直立短耳、细腿和小尾巴。
- 成年卷毛更丰富，但仍紧凑可爱，不能像大型牲畜。

灵息形态：

- 进一步提高可爱度，整体以白色、粉色、淡紫和浅天蓝的柔和云朵色为主。
- 卷毛变成圆润云绒，身体可坐在小云垫上。
- 可使用金色星星、月牙、轻柔漂浮云团。
- 不能变成长脸马、鹿、普通绵羊或阴森漂浮物。
- 动作可坐姿挥蹄、云垫轻弹、云团漂浮、缩进云绒睡觉，与成年站姿和抖毛动作不同。

## 5. 梅花鹿 sikadeer

普通形态：

- 日本梅花鹿方向。
- 栗棕毛色、白色斑点、奶油色腹部、黑鼻尖、大耳和细腿。
- 幼年无角或角很小，成年可有小型枝角。

灵息形态：

- 整体以金色和白色为主，不沿用普通栗棕主色。
- 保留鹿耳、细腿、鹿鼻和轻盈身体比例。
- 可使用金色枝角、白金毛色、星点斑纹、叶芽或吊星。
- 角必须精致、轻巧，不生成威严巨角。
- 动作可用抬蹄、转耳、轻跃、枝角星光摇动，与成年形态区别明显。
- 不得变成神兽坐骑、写实雄鹿或带压迫感的圣兽。

# 五、先建立并锁定角色 DNA

为每只宠物建立一份角色 DNA，至少包含：

- species 和 breed。
- 普通形态基础色板。
- 眼睛、脸纹、耳朵、尾巴、四肢等不可变识别点。
- baby 与 adult 的比例差异。
- magic 的整体换色、轮廓变化、灵息器官、固定纹样和动态特效。
- 各形态禁止项。
- 最终审核通过的身份母版路径。

后续动作生成必须使用审核通过的母版作为身份参考，不能只靠文字重新发明角色。

# 六、三形态评审图

在没有已锁定母版的新任务中：

- 每只动物单独生成一张三形态评审图。
- 左侧 baby，中间 adult，右侧 magic。
- 三形态使用一致视角、基线和视觉尺度。
- 一张图只出现同一只动物的三个形态。
- 普通形态保持物种真实结构的可爱化，不添加多余幻想器官。
- magic 可以整体换色和变异，但必须可爱治愈。
- 使用 2K 或更高源图，再按像素规则缩小。
- 背景使用与主体配色冲突最小的纯色抠像幕。

评审顺序：

1. 物种能否一眼认出。
2. 是否与 assets/pets 中现有宠物像同一款游戏。
3. 是否可爱、治愈、无恐怖感。
4. 三形态是否为同一身份。
5. 幼年与成年是否有真实成长差异。
6. 灵息形态是否足够不同又保留物种。
7. 是否具备可动画化的耳、尾、刺、角、云绒或水带。
8. 在用户明确通过前，不批量制作动作。

# 七、动作源表生成要求

每个形态单独生成一张 4 列 × 5 行动作源表，共 20 帧。

固定行序：

- 第 1 行 normal。
- 第 2 行 happy。
- 第 3 行 eat。
- 第 4 行 sleep。
- 第 5 行 sad。

每行 4 帧必须是同一个连续动作，不是四个无关姿势。

## normal

1. 标准站姿或坐姿。
2. 身体轻微呼吸。
3. 眨眼、转耳、摆尾或灵息器官微动。
4. 回到接近第一帧，保证循环。

## happy

1. 看向玩家。
2. 蓄力、抬爪、扬尾或云垫准备弹起。
3. 轻跳、挥爪、抖毛、晶刺闪动或灵息器官展开。
4. 开心落地或回到稳定姿势。

## eat

1. 注意到食物。
2. 伸爪或靠近嘴部。
3. 咀嚼或鼓起腮帮。
4. 满足地抬头。

默认不在画面中生成食物道具，避免每帧食物形状漂移。除非用户明确要求，使用嘴部、爪部和腮帮动作表达进食。

## sleep

1. 降低身体或坐下。
2. 趴下、蜷起或收拢耳尾。
3. 闭眼呼吸。
4. 保持可循环的睡姿。

## sad

1. 表情变软。
2. 耳、尾、角或背刺轻轻下垂。
3. 身体降低或安静靠近。
4. 停留在需要陪伴的状态。

禁止生成眼泪洪流、伤口、恐怖表情或过度痛苦动作。

动作差异要求：

- 水獭：拍爪、拨水、粗尾摆动；灵息形态用水流和漂浮动作。
- 刺猬：背刺轻抬、卷球、从圆球中探脸；灵息形态用晶刺闪动。
- 小熊猫：举爪、攀爬感、环尾摆动；灵息尾巴始终连接臀部并位于后方。
- 羊驼：普通形态转耳、抖毛；灵息形态坐云、挥蹄、云垫弹动。
- 梅花鹿：普通形态转耳、收腿；灵息形态抬蹄轻跃、枝角星光摇动。

# 八、生图背景要求

动作源表使用纯色抠像背景。

默认背景：

- 纯 #FF00FF 洋红色。
- 整张背景必须完全均匀。
- 无阴影、无渐变、无纹理、无反光、无地面和无光晕。
- 主体与背景颜色必须有足够差异。
- 不要在主体内部使用大面积接近 #FF00FF 的颜色。
- 如果主体本身包含大量洋红、粉紫或紫色，优先更换成不会与主体冲突的纯绿幕等颜色，而不是强行提高抠图容差。

粉色背景只是中间生图素材，绝不能进入正式动作图。正式 PNG 必须为 RGBA 透明背景。

# 九、透明背景和抠图流程

推荐环境：

- Windows Conda 环境 myenv310。
- Python 3.10。
- Pillow 11 或兼容版本。

优先使用已安装的 remove_chroma_key.py 工具；如果工作区已有验证过的宠物后处理脚本，优先复用，不要重复写临时脚本。

常规不冲突颜色可先尝试：

--auto-key border
--soft-matte
--transparent-threshold 12
--opaque-threshold 220
--despill

但禁止不检查结果就批量接受软蒙版。软蒙版可能把主体中的暖色、粉色、紫色、橙色、云绒或晶刺误判为背景，造成脸、耳朵、身体、刺或特效半透明。

每张透明源图必须同时检查：

- 四角和背景区域 alpha 为 0。
- 主体内部没有透明洞。
- 脸、眼睛、耳朵、尾根、四肢和主要纹样完整。
- 暖色高光、紫色身体、粉紫云绒、橙金晶刺没有被削掉。
- 主体边缘没有明显洋红色杂边。
- 不应出现大面积 1 至 254 的意外半透明像素。
- 在黑色和白色底上分别预览，避免透明查看器造成误判。

当前已验证的特殊规则：

下面 4 张源图禁止使用通用软蒙版，必须使用边缘自动取色、容差 80 的二值硬色键，不启用 soft-matte：

- alpaca-adult-actions-source-v1.png。
- alpaca-magic-actions-source-v1.png。
- hedgehog-baby-actions-source-v1.png。
- hedgehog-magic-actions-source-v1.png。

原因：

- 成年羊驼的暖色会被软蒙版侵蚀。
- 灵息羊驼的粉紫云绒、耳朵和脸会被软蒙版挖空。
- 幼年刺猬的杏色暖色会被误伤。
- 灵息刺猬的紫色身体和橙金晶刺会被误伤。

对应硬色键参数：

--auto-key border
--tolerance 80
--force

不使用 --soft-matte。

硬色键结果必须再次人工检查。若边缘仍有洋红杂边，先确认它是背景溢色还是角色本身的合法粉色细节；不得为了去掉一像素杂边再次把主体抠空。

如果主体颜色与抠像色严重冲突，最优先方案是回到源图更换抠像背景重新生成，而不是无限提高容差。

# 十、切片、缩放和对齐

处理动作源表时：

1. 不要盲目平均切成 4 × 5；先根据透明度或主体投影确认真实网格边界，避免相邻格碎片混入。
2. 每格只保留对应角色和该帧合法特效。
3. 计算每帧不透明包围盒。
4. 同一形态的 20 帧使用同一个缩放系数。
5. 水平居中，普通站姿底部对齐。
6. 轻跳、漂浮和云垫弹动要保留相对垂直位移，不能每帧强制贴底。
7. 主体和特效不能碰到 128 × 128 画布边缘。
8. 缩放使用 nearest-neighbor。
9. 不使用双线性或双三次插值。
10. 输出 RGBA PNG。

状态横条：

- 每帧 128 × 128。
- 4 帧从左到右合并。
- 最终尺寸严格为 512 × 128。
- 每个形态生成 full.png。
- 每只宠物生成 preview.png。

可复用工具：

- tools/pets/process_animation_sources.py。
- tools/pets/verify_animation_outputs.py。
- tools/pets/verify_pet_assets.py。

# 十一、正式资源整理

最终通过审核的图片必须复制到 assets/pets/<species>/。

只放运行时所需文件：

- baby、adult、magic 下的五张状态精灵图和 full.png。
- 根目录 preview.png。
- manifest.json。
- 对应 CSS。
- 对应 README。

不要把下面内容混入正式宠物目录：

- 粉色背景原图。
- 透明源动作大图。
- 测试容差图。
- GIF 预览。
- processing.json。
- verification-report.json。
- 失败版本或旧母版。

仍需要保留的锁定母版、粉色动作源表和通过检查的透明动作源表，统一归档到 assets/pets/_generation-sources/，不要继续放在 design 目录。

manifest.json 必须声明：

- type 为 sprite-animation-set。
- 正确的 species 和 displayName。
- frameDurationMs 为 500。
- framesPerAnimation 为 4。
- layout 为 horizontal。
- 三形态和五状态的相对路径。
- frameWidth 和 frameHeight 为 128。

CSS 必须：

- 使用 128 × 128 容器。
- 背景尺寸为 400% 100%。
- 映射三形态和五状态。
- 2 秒完成四帧循环。
- 不影响其他宠物的 class 和 keyframes。

README 必须说明物种、三形态、五状态、尺寸、帧速率、透明背景和 CSS 使用方式。

# 十二、自动验证

最终至少验证：

- 每只宠物存在 3 个形态。
- 每个形态存在 normal、happy、eat、sleep、sad 和 full.png。
- 每张状态图是 512 × 128 RGBA PNG。
- 每张 full.png 和 preview.png 是 128 × 128 RGBA PNG。
- 每张状态图能精确拆成 4 个 128 × 128 帧。
- 四角透明。
- 主体没有越界或裁切。
- 主体内部不存在异常透明洞。
- GIF 或逐帧预览动作连续。
- manifest 中每个 src 文件真实存在。
- CSS 中每个图片路径真实存在。
- species key 与目录名一致。
- 旧宠物资源和旧存档逻辑没有被修改或破坏。

当前完整批次的基准数量：

- 5 个物种。
- 15 个形态。
- 75 张状态精灵图。
- 300 张独立动画帧。
- 75 个四帧 GIF 预览。
- 验证错误必须为 0。

# 十三、人工验收

必须查看而不能只依赖脚本：

- 三形态 preview。
- 每个形态至少 normal、happy、sleep 三组横条。
- 红熊猫 magic 的每一帧尾根。
- 灵息羊驼的脸、耳朵和粉紫云绒。
- 幼年刺猬的杏色脸和肚皮。
- 灵息刺猬的紫色身体、天蓝与橙金晶刺。
- 水獭与梅花鹿灵息形态的白色主体边缘。
- 黑底和白底透明预览。
- 1 倍、2 倍、4 倍像素化显示。
- 500ms 正式速度和快速预览。

任何一项失败，只修复失败的物种、形态、状态或单帧，不要无理由重做已经通过的普通形态。

# 十四、交付顺序

固定按照以下阶段执行：

1. 检查现有资源和 species key。
2. 输出角色 DNA 和三形态设计规格。
3. 生成或确认三形态母版。
4. 等待外观审核。
5. 先生成三形态 normal 动画样例。
6. 等待动作样例审核。
7. 生成完整 4 × 5 动作源表。
8. 去除抠像背景并人工检查透明度。
9. 切片、统一缩放、对齐和打包。
10. 运行自动验证。
11. 将通过的正式 PNG、manifest、CSS 和 README 放入 assets/pets。
12. 检查运行时路径。
13. 汇报最终物种目录、图片数量、抠图方式、验证结果和仍未接入的功能。

除非用户明确要求，整理图片到 assets/pets 不等于自动把新宠物加入领养列表、图鉴、文本或剧情。不要擅自扩大接入范围。

如果用户明确要求“接入游戏”，图片整理完成后还必须继续检查并修改：

- 运行时物种中央清单、英文 key 与中文显示名。
- 特别陪伴的固定剧情动物选择。
- 领养登记表的许愿物种选择。
- 灵息图鉴物种、三形态解锁项、名称、像素角标和精灵图路径。
- 物种外观注入映射，确保 AI 生成剧情时获得普通/灵息形态的完整固定外观。
- assets/pets/text/info.txt 的允许 species、物种动作语言与外观硬规则。
- assets/pets/text/world.txt 的物种标签、气质参考、真实身体动作与非绑定灵息适配。
- 固定剧情生成器、剧情弧、宠物动作句、宠物语录和验证器的物种清单。
- assets/pets/text/pet_info_<species>.txt：15 个主线里程碑、6 条支线、23 段可读剧情正文、33 条角色语录与 45 条宠物语录。
- 根 README 的物种数量、选择范围、新宠物外观与动画说明。
- 全局搜索旧物种白名单，不能只修改一个下拉框。

固定剧情与 AI 剧情的文风另外遵守：

- 从正在发生的动作、变化或对话开始，不先解释人设与主题。
- 正文第一句不得照抄或改写标题、summary、opening_cause，也不得用任务、目标、规定、分工或“表示反对”等总结句代替现场动作。
- 固定剧情的蛋由玩家进入游戏时另行选择；`pet_info_<species>.txt` 不写固定 `egg` 字段，正文也不预设蛋色。运行时必须把玩家选择写入 `pet_card.egg` 并据此显示蛋图片。
- 固定剧情选择页只开放玩家名、蛋外观和动物剧情；宠物名、性别、性格、能力、主线与支线均随固定剧本确定，界面必须明确告知。
- 自由生成登记表的基础项为玩家名、蛋外观、雌雄备选名、叙事人称、模型与重试次数；详细许愿才开放物种、性别和灵息能力，保留“随机”时交给模型决定。
- 用“具体事件→生活反应→新变化”推进；线索、反转和选择都落在可见动作与现场后果上。
- `{{user}}` 与 `{{char}}` 平等、活泼、有自尊且都主动做事；两人会追问、打断、拆台、补位、承认判断失误与直接表达在意。
- 冲突来自两个都合理的具体目标暂时相撞，并通过试错、分工、选择与修复解决；不用权力差异、说教、强制亲密或拖延误会制造张力。
- 对话保持高密度、自然口语化与来回反应，避免一人长篇解释、另一人被动执行。
- 关系只通过共同时间、具体选择、分歧、支持与修复发展，不由旁白宣布“羁绊加深”。
- 结尾保留一个正在发生的小动作、新计划或具体邀请，不以“等待回应”或抽象感悟收束。

最终答复必须给出：

- 正式资源保存路径。
- 使用的母版和生图方式。
- 抠图方式及特殊参数。
- 最终文件数量。
- 自动验证结果。
- 已人工查看的关键图片。
- 是否已经接入运行时代码。
